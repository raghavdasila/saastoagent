Terminology

These terms should remain stable in downstream design and code.

Corpus
The chat-first agentic app used to configure, design, build, evaluate, deploy, operate, and improve agents. Its primary agent is scoped by the active RouteDeck node.
Agent
A runtime agent deployed by Corpus. It uses models, connected sources, tools, and RouteDeck interaction state.
Agentic app
A separate application category with an agentic interaction model. It is not the default name for a deployed agent.
Feature
A bounded product capability that owns RouteDeck nodes, agent policies, operations, surfaces, providers, guards, and outgoing transitions.
Navgraph
The compiled legal navigation topology: nodes connected by operation outcomes and transitions.
Surface
A RouteDeck-declared UI projection with typed props and affordances, rendered by a product or standard component library.
Source manifest
Normalized discovery output from an API, database, knowledge base, or MCP server before it is designed into an agent.
Capability
A RouteDeck grouping of operations, surfaces, and policies declared within a node. It is not automatically a Corpus feature.
Agent Configuration
The versioned contract for an agent's identity, instructions, Navgraph, node scopes, sources, operations, policies, surfaces, model roles, memory, access, channels, and lineage.
Evalset
A versioned collection of evaluation cases, inputs, binding profiles, expected outcomes, assertions, and readiness rules.
Channel
A configured delivery and interaction boundary through which an agent communicates, including identity, credentials, supported surfaces, and delivery semantics.
Memory
Agent-owned retained context governed by explicit scope and retention. It is distinct from sourced knowledge and reviewed learning.
Use this to flag names that are overloaded or still wrong.

What “capability” should mean

The confusion came from using one word for three different layers. They must stay separate.

Before design

Source manifest

What Corpus discovered from a connected source.

  • OpenAPI endpoints and schemas
  • Database tables, relations, and bounded operations
  • GRAG sources and query/evidence contracts
  • MCP tools, resources, and prompts
During design

Agent design selection

The approved subset of source-manifest entries and the rules for how an agent may use them.

  • Included and excluded entries
  • Agent instructions
  • Safety and review requirements
  • RouteDeck node placement
Inside RouteDeck

RouteDeck capability

A named grouping declared on a RouteDeck node.

  • Operation references
  • Surface references
  • Agent-policy references
Recommendation: remove the proposed Capability Catalog feature. Source features expose and curate source manifests. The Agent Designer turns approved manifest entries into RouteDeck nodes, operations, surfaces, policies, and capabilities.

A RouteDeck capability is useful when

A node needs a coherent named ability such as “inspect order” that brings together legal operations, relevant surfaces, and agent guidance.

It is not

A marketplace, source catalog, discovery database, entire feature, or generic bucket containing every external action known to Corpus.

Use this to decide whether “source manifest” is the right pre-design term.

Deployed agents + RouteDeck

A deployed agent is an agent. RouteDeck governs its interaction state around the model and connected-source execution; it does not rename the agent into an agentic app.

Runtime responsibility

RouteDeck primarily owns

  • Current node and interaction state
  • Legal operations and guarded identifiers
  • Needs-input and review state
  • Surface projection and affordances
  • Navigation, recovery, and diagnostics

The deployed agent still owns

  • Model reasoning and response composition
  • Product instructions and language
  • Source/tool selection within legal context
  • Domain interpretation
  • Calling host-owned source bindings

Standard surface library

Deployed agents can begin with a shared mobile-ready surface library. RouteDeck projects the correct typed surface for the current interaction state.

  • ConversationAgent and user messages, streaming state, suggested actions.
  • Entity listSelectable records exposed by a trusted provider.
  • Entity detailStructured view of one selected record.
  • FormTyped missing inputs, with private fields kept server-authorized.
  • ReviewHuman confirmation for consequential operations.
  • ResultStructured operation result with safe public presentation.
  • StatusLong-running work, readiness, and progress.
  • EvidenceKnowledge citations, provenance, and evidence graph views.
  • RecoveryExplicit failure, blocked action, retry, or alternate next step.
Later extension: an agent may register product-specific custom surfaces. The standard library remains the baseline, not a restriction that every domain must look identical.

Agent-owned memory

Corpus has memory for its owner. Each deployed agent has separately configured memory scopes and retention. Knowledge, memory, and learning remain distinct.

Channel-compatible interaction

Each deployed revision binds to validated channels whose identity, delivery, and supported-surface contracts are explicit in Agent Configuration.

Record which surface types are truly standard and which belong to particular agents.
